# D0.1 — CPF do doador (adendo à D0 / Identidade)

Responsável: **Gabriel**. Não depende de nenhuma demanda em aberto.

> **Não impacta o andamento de D1, D2, D3, D4 ou D5 — confirmado abaixo.**
> Pode ser feita a qualquer momento, na ordem que o Gabriel preferir, sem
> travar nem ser travada por nenhuma outra demanda em curso.

## Por que "D0.1" e não uma demanda nova

Isso é um item que ficou faltando dentro do escopo da própria D0 (Base — módulo
Identidade, que já é do Gabriel): a D0 tratou do rename de roles, mas não
tratou do cadastro de doador em si, que continuou exatamente como veio do
`fiap-cloud-games`. Por isso entra como adendo da mesma demanda, não como uma
nova numeração solta na fila (d7 seria a leitura errada de que isso é uma
etapa nova, depois de d6 — não é: é um retorno a algo que já era escopo do
Gabriel em d0).

## Objetivo

Adicionar o campo CPF (com validação de formato) ao cadastro de doador —
requisito funcional explícito do edital que ficou de fora do escopo herdado
do `fiap-cloud-games` e não foi mapeado em nenhuma demanda (d0–d6).

## Como foi encontrado

Achado numa auditoria comparando o edital
(`../../../edital/HACKATHON_11NETT.pdf`, item 3 "Cadastro de Doador") com as
demandas d0–d6: o edital exige Nome Completo, Email (único), **CPF (validar
formato)** e Senha (hash). A entidade `Usuario` — herdada do boilerplate
`fiap-cloud-games` (plataforma de jogos, nunca teve esse campo) — só tem
`Nome`, `Email` e `SenhaHash`. Nenhuma das demandas d0–d6 menciona CPF.

## Contexto

- Campos hoje: `src/ConexaoSolidaria.Domain/Identidade/Entities/Usuario.cs`
  (Nome, Email, SenhaHash, Perfil, Ativo)
- Cadastro público: `POST /api/auth/registrar` (`AuthController` →
  `CriarUsuarioUseCase`) — já atribui `PerfilUsuario.Doador` por padrão, isso
  está correto e não precisa mudar
- Precisa de: novo Value Object `Cpf` (seguir o padrão de `Email`/`SenhaHash`
  já existentes em `Domain/Identidade/ValueObjects/`), com validação de
  formato de verdade (dígitos verificadores, não só "11 dígitos")

### Raio de impacto (tudo dentro do módulo Identidade)

- `Usuario.cs` (novo campo + validação)
- `CriarUsuarioRequest` (DTO) + `CriarUsuarioRequestValidator`
- `CriarUsuarioUseCase`
- `UsuarioConfiguration` (mapeamento EF) + nova migration no schema
  `identidade` — inclui ajustar o `HasData` do usuário admin de seed, que
  precisa ganhar um CPF fixo
- `e2e/smoke-test.sh`: todos os payloads de `POST /api/auth/registrar`
  (cenários A, R, S, T) precisam do campo novo, senão o script quebra
- Testes unitários em `tests/ConexaoSolidaria.Tests/Identidade/`
  (`UsuarioTests`, `CriarUsuarioUseCaseTests`, validator)

Nada disso é tocado por nenhuma outra demanda em aberto — ver análise abaixo.

## Análise de risco / janela de tempo

Levantamento feito a pedido do Gabriel, para confirmar que dá para deixar
isso por último (depois de D2–D5) sem atrapalhar ninguém.

- **Impacto em D1/D2/D3/D4/D5: nenhum.** D0 — única demanda que já mexeu no
  módulo Identidade — está fechada e mergeada. D1 (Campanha) e D2
  (Doação/Worker) referenciam usuário só pelo `Guid` (`IdDoador`), nunca
  instanciam nem leem campos de `Usuario` — confirmado por busca no
  repositório inteiro (`new Usuario(` só aparece dentro do próprio módulo,
  em `UsuarioTests.cs`). D3/D4/D5 não tocam em código de aplicação da
  Identidade. **Dá para fazer a qualquer momento, inclusive em paralelo com
  D2–D5, sem gerar conflito de merge com o trabalho de mais ninguém.**
- **Migration de banco: sem conflito.** Cada módulo tem schema/DbContext
  próprio (`identidade`, `campanha`, `doacao`) — uma migration nova em
  `identidade` não toca nas migrations que D1/D2 já criaram em `campanha`/
  `doacao`.
- **O único prazo real é interno à D6, não os colegas**:
  - `e2e/smoke-test.sh` é o script de validação da API de Identidade (o
    `CLAUDE.md` exige rodá-lo antes de qualquer PR que mexa nela) — se CPF
    virar campo obrigatório, o script quebra até ser atualizado junto.
  - Se o README, prints do Swagger ou qualquer coleção Postman/Insomnia
    usada no vídeo forem preparados **antes** dessa mudança, ficam
    desatualizados e precisam ser refeitos.
  - O roteiro obrigatório do vídeo (edital, item 3 dos entregáveis) **não**
    exige mostrar o cadastro de doador — só autenticação/token, criação de
    campanha e simulação de doação — então isso não trava a gravação em si,
    só a precisão da documentação escrita.
- **Conclusão**: pode ficar para o fim da fila, mas precisa estar
  **concluída antes de a D6 travar o README e gravar o vídeo** — não antes
  de D2/D3/D4/D5, que seguem soltas independente disso.

## Decisões

- 2026-09-28 — **CPF duplicado é bloqueado**, mesmo o edital só exigindo
  unicidade explícita para o e-mail. Justificativa: CPF identifica uma
  pessoa física de forma única no mundo real — permitir duas contas de
  doador com o mesmo CPF abriria brecha para fraude/duplicidade de cadastro
  sem nenhum ganho, e o custo de implementar (um índice único + uma
  verificação a mais no use case, exatamente espelhando o que já existe para
  `Email`) é mínimo. `CriarUsuarioUseCase` verifica e-mail duplicado primeiro
  e CPF duplicado em seguida, cada um com sua própria `ConflictException` e
  mensagem.
- 2026-09-28 — CPF do admin de seed fixado em `111.444.777-35`: é o CPF de
  teste mais comumente usado em documentação/exemplos brasileiros (passa nos
  dígitos verificadores, mas não corresponde a nenhuma pessoa real
  conhecida) — não havia CPF real disponível nem sentido em inventar um
  válido "sério" para um usuário de sistema.
- 2026-09-28 — `Cpf.Valor` armazena só os dígitos (sem pontuação), mesmo
  aceitando entrada formatada (`"111.444.777-35"`) — mesma lógica de
  normalização que `Email` já usa (trim + lowercase). Simplifica unicidade
  no banco (`char(11)`) e evita duas linhas com o "mesmo" CPF em formatos
  diferentes escaparem do índice único.

## Validação ponta a ponta

Rodada nesta sessão, no ambiente de execução remota do Claude Code:

- Docker (`dockerd`) não sobe pelo `service docker start` padrão do
  container (`ulimit: error setting limit (Operation not permitted)`) — mas
  sobe rodando `dockerd` direto em background, contornando o script de init.
  Registrado aqui porque não é o procedimento documentado em `e2e/README.md`
  e outra sessão pode esbarrar no mesmo bloqueio.
- `dotnet` não está instalado no PATH deste container — build, testes e
  geração da migration rodaram dentro do próprio container
  `mcr.microsoft.com/dotnet/sdk:10.0-noble` (a mesma imagem base do
  `Dockerfile` do projeto), montando o repositório e confiando o CA do proxy
  de egress do sandbox (mesmo mecanismo que `docker/certs/README.md` já
  documenta para o `docker build`).
- `dotnet build ConexaoSolidaria.slnx -c Release`: **0 erros** (depois de
  ajustar 9 arquivos de teste de outros use cases de Identidade —
  `LoginUseCaseTests`, `RefreshTokenUseCaseTests`, `AlterarSenhaUseCaseTests`,
  `InativarUsuarioUseCaseTests`, `AtivarUsuarioUseCaseTests`,
  `ObterContaUseCaseTests`, `ObterUsuarioPorIdUseCaseTests`,
  `ListarTodosUsuariosUseCaseTests`, `TornarUsuarioAdministradorUseCaseTests`
  — que também instanciam `Usuario` diretamente e quebraram de compilar com
  o novo parâmetro `cpf` do construtor; fora do raio de impacto inicialmente
  mapeado acima, mas nenhum teve o comportamento alterado, só o argumento
  novo)
- `dotnet test tests/ConexaoSolidaria.Tests`: **228 testes, 0 falhas**
- `bash e2e/smoke-test.sh` (stack completo via `docker-compose`: Postgres +
  RabbitMQ + build das imagens `migrate`/`api` + bateria de cenários HTTP
  incluindo os novos payloads com `cpf`): **PASS=36 FAIL=0** na primeira
  execução limpa depois do fix abaixo.
  - Achado no caminho: a primeira rodada deu **FAIL=36** — todo o script
    (não só os cenários de CPF) falhava com "conexão recusada" em toda
    chamada HTTP. Investigando, o container `api` derrubava logo na subida
    com `OptionsValidationException: 'RabbitMqSettings' ... Username ...
    Password ... required` (exit code 139) porque o `.env` temporário que o
    próprio `smoke-test.sh` gera nunca ganhou `RABBITMQ_USER`/
    `RABBITMQ_PASSWORD` quando o RabbitMQ entrou no projeto (D2) —
    `docker-compose.yml` espera as duas para montar `RabbitMqSettings__*`.
    Bug pré-existente, sem nenhuma relação com CPF (a própria D2 já registra
    em `visao-geral.md` que nunca chegou a rodar o smoke test ponta a
    ponta). Corrigido em `e2e/smoke-test.sh` (duas linhas a mais no `.env`
    gerado, mesmo padrão das outras credenciais aleatórias) — sem essa
    correção não dava para validar a própria D0.1 de verdade, então ficou
    dentro do escopo desta sessão consertar.
  - Confirmado manualmente antes do fix: com o `.env` "quebrado" (sem
    RabbitMQ), `docker compose logs api` mostra a exceção acima; com as
    variáveis presentes, a API sobe normalmente (`Application started`,
    `Bus started: rabbitmq://rabbitmq/`) e responde no `:8080`.
  - Cenário A (registrar doador com CPF) → 201, CPF gravado e único;
    cenário B (mesmo e-mail, mesmo CPF) → 409 (rejeitado pelo e-mail
    duplicado, que é verificado primeiro); cenários R/S/T (com CPF válido
    mas outras falhas de validação) → 400; login do admin de seed (CPF fixo
    `111.444.777-35`) → 200, sem quebrar nada do fluxo existente.
